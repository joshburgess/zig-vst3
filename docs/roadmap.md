# Roadmap

This file tracks current project work and release readiness.

## Current Focus

`zig-vst3` is the raw VST3 API package. `zig-vst3-plugin` is the higher-level plugin framework package. Both are now exercised by validator-passing example bundles and the public CI matrix.

Near-term work should stay focused on finishing release confidence before adding broad new features:

- Keep the Zig version pinned in `docs/toolchain.md` and CI. Update it only through a dedicated PR.
- Keep the VST3 SDK version pinned in `scripts/fetch_sdk.*` and documented in `docs/toolchain.md`.
- Keep host smoke results in `docs/host-matrix.md`.
- Keep public API docs synchronized with framework changes.

Configurable bus layouts, background resource jobs, immutable exchange, deferred reclamation, fixed-rate conversion, latency notification, resource persistence, C kernel integration, CPU dispatch, scoped denormal control, and headless C++-to-Zig DSP parity tooling are implemented. ## Validation Tiers

- Tier 0: `zig build` and `zig build test`.
- Tier 1: `zig build raw-api-abi`.
- Tier 2: `zig build validator` and `zig build validate-examples` on platforms where Steinberg validator support is available.
- Tier 2 optional: `zig build pluginval-examples` and `zig build pluginval-strict-examples` when Tracktion pluginval is installed.
- Tier 3: real host smoke tests recorded in `docs/host-matrix.md`.

For normal code changes, run the smallest tier that covers the changed behavior. For release work, use `scripts/raw_api_release_check.sh` and the checklist in `docs/release-checklist.md`.

## Framework API Symmetry

The current `zig-vst3-plugin` public surface has had a symmetry pass across `process.zig`, `parameters.zig`, `state.zig`, `units.zig`, and `plugin.zig`.

Current interpretation:

- `ParameterSet`, `ParameterView`, and `ParameterEditor` share the same metadata, validation, conversion, and reflected parameter-change construction surface. `ParameterEditor` adds mutation, reset, copy, and process-change application methods.
- `PluginInstance` exposes the practical instance-bound parameter, unit, program-list, program, state, lifecycle, topology, process, and metadata helpers without forwarding every value-level helper as an alias.
- `ProcessorRuntime` owns format-neutral prepare, activation, processing, flush, state-restore, latency, tail, reset, release, and teardown ordering. `OfflineRenderer`, `StandaloneRuntime`, `Vst3Processor`, the LV2 `CoreAdapter`, and the Audio Unit render core consume the same lifecycle. The Audio Unit render core covers negotiated sample rate and block size, initialize and uninitialize, f32 and f64 deinterleaved processing, static main and auxiliary buses, process attachments, deterministic failure silence, and statistics. SDK-checked AUv2 declarations and dispatch cover lifecycle, static bus and planar stream properties, maximum frames, latency, tail, input pull callbacks, reflected parameter metadata, immediate get and set, bounded sample-offset point and ramp automation, Core Foundation class-info state, bounded property listeners, pre-render and post-render notifications, and allocation-free multi-output rendering. Ramps use a shared process attachment with signed starts, linear interpolation, deterministic event precedence, and next-block boundary persistence. A timestamp-keyed fixed-storage cache supports main-first, auxiliary-first, and repeated output-bus requests with one processor execution and one automation application per block. Owning component factories, registered Mono Gain and Auxiliary Output Splitter `.component` bundles, plist and symbol validation, dynamic-library host fixtures, and cross-target component builds are implemented. External AU host validation remains. The LV2 core adapter covers static f32 audio and control ports, bounded Atom Sequences, segmented transport, typed Patch Set and Get properties, block-size options, declaration-driven freewheeling mode, latency, parameter and component state, bounded Worker scheduling, and Programs enumeration and selection. Dynamic fixtures cover Patch timing and hostile messages, immediate offline and delayed threaded Worker delivery, response lifetime, end-of-cycle ordering, simultaneous UI instances, and repeated UI close and reopen lifecycles. The LV2 UI adapter bridges the toolkit-neutral editor to parent attachment, controls, Programs selection, idle, resize, show, hide, and teardown. The VSTGUI backend supplies a linked parameter editor and native widget. Generated metadata covers ports, Patch access, presets, Programs, and the separate UI resource. External-host validation, metadata lint, advanced custom components, remaining extensions, and dynamic topology remain.
- `StandaloneRuntime` maps checked realtime device blocks into the processor runtime. `DeviceChannelRouter` maps flat physical channels onto main and auxiliary buses with fixed storage and whole-device failure silence. `Midi1BlockScheduler` and `UmpBlockScheduler` bridge one device producer to one audio-thread consumer, convert absolute timestamps to sample offsets, retain future and capacity-limited packets, and count rejected callback packets. The UMP path preserves all four packet widths without narrowing non-event messages. `StandaloneApplication` coordinates transactional audio-device and processor lifecycle. Audio callback, timestamped MIDI 1 and UMP device, deterministic failure silence, callback-failure, bounded discovery catalog, deterministic selection fallback, versioned selection persistence, and transactional recovery contracts are format neutral. `DeviceRecoveryController` commits only successful fallback or restart operations, retries failures, and restores a returning preferred device. A bounded multi-source monitor connects retained CoreAudio, WASAPI, ALSA PCM, CoreMIDI, WinMM, and ALSA RawMIDI failures to same-selection recovery without consuming partial observations. CoreAudio keeps processor callback rejection separate from device-side failures. `StandaloneWindow` and `StandaloneShell` add top-level native-parent ownership, bounded window events, visibility, resize, scale, focus, quit ordering, failure polling, and recovery application. Versioned selection distinguishes unified devices from independent capture and render endpoints. Optional modules provide CoreAudio, CoreMIDI, and an AppKit top-level window on macOS, event-driven shared-mode WASAPI, timestamp-scheduled WinMM MIDI 1, and a Win32 top-level window on Windows, and runtime-loaded ALSA PCM, timestamp-scheduled RawMIDI, X11, and Wayland windows on Linux. Both native MIDI 1 schedulers use a fixed-capacity queue, stable equal-time ordering, nonblocking producer admission, cancellation on replacement or close, and retained output statistics. A shared VST3 bridge supplies the Wayland host, frame, native objects, resize path, and delegated run loop. The bounded Steinberg run-loop driver supplies file-descriptor and timer integration for both VSTGUI Linux paths. Optional PipeWire integration, native Windows MIDI Services and Linux UMP bindings, sustained cross-device drift compensation, physical scheduler and recovery confirmation, and physical window integration remain.
- `UnitSet` retains the broad program metadata lookup surface. `PluginInstance` forwards the host-facing and instance-useful paths, especially list-id, list-name, unit-id, and unit-name program metadata paths.
- `ProcessContext` provides direct input, output, parameter-change, input-event, output-event, timing, segment, and writer helpers. The current distinction between input events, output events, and generic event views is intentional.
- `state` value types provide direct report/header helpers, while `PluginInstance` binds the helpers that need the reflected parameter count.

The standalone lifecycle fixture now covers a callback during stop, stale callbacks after stop and failed startup, processor rollback, clean restart, and successful retry. Physical callback timing and recovery remain external checks.

Do not add aliases only to make every type expose every spelling. Add new API only when a real workflow needs the helper at that API boundary.

## Non-goals

- Hosting plugins. This project builds plugins, not hosts.
- VST2 compatibility.
- A mandatory GUI toolkit. VSTGUI is an optional reference adapter, and users can provide another toolkit.
- Plugin sandboxing or out-of-process hosting.
